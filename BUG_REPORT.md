## 2. Fixed bugs

### B1 - Presets were never saved (logic)

- **Symptom**: pressing *Save* on a preset then *Load* restored the old values;
  the preset file never changed.
- **Cause**: `RailwayTool.drawPresets()` copied `config.preset1..3` into a local
  `RailConfig.Data[] slots` array and assigned `slots[idx] = snapshotData()`.
  The assignment only replaced an element of the local array; the `config`
  fields were never written.
- **Fix** (`4fefed3`): `preset(int)` / `setPreset(int, Data)` read and write the
  config fields directly, followed by `persistConfig()`.
- **Re-test (in game)**: scene `presets` saves a density-9 / nature preset,
  changes the tool to density 3 / classic, reloads the preset, and re-reads the
  JSON from disk. All three checks pass (`preset restores density`,
  `preset restores style`, `config saved to disk`).

### B2 - Hand-edited config could index UI arrays out of range (crash)

- **Symptom**: a config with `styleIndex`/`orientIndex` beyond its combo range
  is loaded straight into the ImGui combo state.
- **Cause**: `RailConfig.load()` trusted the JSON; `restoreConfigOnce()` copied
  the raw indices into the `ImInt` selectors.
- **Fix** (`4fefed3`): `RailConfig.sanitize()` clamps every index (and every
  preset on load); `applyData()` clamps each field as well.
- **Re-test**: the in-game suite loads the persisted config back through
  `RailConfig.load()` and compares it with the live tool state.

### B3 - Support soil and headroom air erased neighbouring rail decor (world bug)

- **Symptom**: rebuilding or crossing a line could remove a wall/shelf/door of
  the neighbouring line, then leave the core without its lateral decor.
- **Cause**: `ClassicDesign.ColumnWriter.column()` guarded only the core write;
  the support soil (`startY`) and the headroom air (`startY + 2`) were written
  unconditionally and could overwrite `RAIL_FAMILY` blocks of another column.
- **Fix** (`40919a2`): both writes are now skipped when the target cell belongs
  to the rail family. `rail_sim.build_column()` received the same guard.
- **Re-test (A/B, actually executed)**: with the old simulator guard removed,
  `stupid_stress.py` reports 50 `rail detruit` violations; with the guard in
  place the same suite is green.
- **Re-test (in game)**: scene `cross` builds a north-south line, then an
  east-west line across it. The second plan replaces 2 wall blocks at the
  junction and zero cores; all 17 cores of the first line are still coral in
  the world afterwards, and the junction is a single connected ribbon
  (`replaced=0`, `first line intact after the crossing`, `crossing is one
  junction`).

### B4 - Chunk render overrider leaked and could crash the client (Axiom lifecycle)

- **Symptom**: after the ghost preview emptied, the tool kept the global
  render-override lock. Any later acquire (same tool or another Axiom tool)
  throws; the old code also assumed acquisition always succeeded.
- **Cause**: `RailwayTool` acquired the lock in `setGhost()` but never released
  it outside `reset()`; `Axiom.acquireChunkRenderOverrider` called the throwing
  Axiom API directly.
- **Fix** (`40919a2`, `ae438bb`): named lock (`OVERRIDER_ID`), boolean
  acquisition wrapper that catches `RuntimeException | Error`, `releaseGhost()`
  called when the ghost is empty, when the trace disappears and from `reset()`.
- **Re-test (in game)**: after every scene the suite tries to acquire the
  render lock under an independent id; it succeeds in all fourteen scenes,
  which proves the tool released it (`render lock released (...)`).
  `acquire` throwing when held and `release` being name-checked were also
  confirmed from the shipped 5.4.2 bytecode.

### B5 - Ghost cells were cleared without holding the lock (state bug)

- **Cause**: `ghostPositions` survived a release, so `clearGhost()` could call
  `setBlockRenderOverride` after the lock had been released or taken by another
  tool.
- **Fix** (`ae438bb`): `clearGhost()` returns immediately when the lock is not
  held, and always clears the position set.
- **Re-test (in game)**: after every build the suite reads the tool's
  `ghostPositions` set; it is empty in all fourteen scenes
  (`ghost cleared (...)`).

### B6 - Preview exception escaped `render()` (crash / broken panel)

- **Cause**: `recompute()` ran unguarded from the render tick; a failure left
  stale plan/warning/length state and threw into the render thread.
- **Fix** (`40919a2`, `ae438bb`): `render()` catches `RuntimeException`, clears
  plan/ghost/spline state and surfaces a localized `ui.error` status; `warning`
  and `splineLength` are reset on every failure path.
- **Re-test (in game)**: `render()` is the entry point used by every scene; 13
  recomputes ran on the render thread with no exception and no error line in
  `latest.log` (checked by `no mod errors in log`).

### B7 - Axiom build failure escaped `confirm()` (crash on Enter)

- **Cause**: `Axiom.push()` was called unguarded; an exception from the edit
  pipeline propagated out of the tool callback.
- **Fix** (`ae438bb`): the push is wrapped, reports `ui.error` and keeps the
  plan intact so the player can retry.
- **Re-test (in game)**: every scene confirms through the real Axiom pipeline
  (2 690 blocks placed across the run); an extra `confirm()` on an
  empty plan is harmless.

### B8 - Block picker could store air or null (world bug)

- **Cause**: the *pick active block* buttons assigned `Axiom.getActiveBlock()`
  without validation; air/null then became the uniform fill or a soil slot.
- **Fix** (`40919a2`): null and air are rejected.
- **Re-test (in game)**: scene `edges` aims at the sky and clicks; the tool
  reports no target and adds no control point (`sky click adds no point`).

### B9 - Lock acquisition retried for every ghost block (performance)

- **Cause**: when another Axiom tool held the render lock, `setGhost()` retried
  `acquire()` for up to 6 000 ghost cells per recompute, each throwing an
  exception.
- **Fix** (`96ec039`): one attempt per preview (`ghostDenied`), so the panel
  stays responsive.
- **Re-test (in game)**: the 801-block line (`long` scene) previews in 4 ms;
  worst recompute over the run is 45 ms, first one included.

### B10 - O(n^2) connectivity checks on large selections (performance)

- **Cause**: `LCorners.purge()` re-flooded the whole remaining trace for every
  candidate corner; `LCorners` also kept the wool set in a mutable static field
  shared by all calls.
- **Fix** (`4fefed3`): the global guard is `keepsConnected()` - a flood limited
  to the 26 neighbours with early exit - after a single up-front connectivity
  check; the wool set is an explicit parameter.
- **Re-test**: `parityCheck` requires an identical block map and passes, and in
  game the 801-block line plans in 4 ms (801 blocks, 89 cores).

### B11 - Nondeterministic stress corpus (test reliability)

- **Cause**: `stupid_stress.py` seeded scenarios from Python's randomized
  `hash()`, so failures were not reproducible between runs.
- **Fix** (`40919a2`): seeds use `zlib.crc32(...)`, stable across processes.

### B12 - CI did not build what was shipped (release pipeline)

- **Cause**: the 47 MB Axiom jar and generated logs were committed; `gradlew`
  was stored without the executable bit; the jar was not gated on parity.
- **Fix** (`40919a2`): Axiom is downloaded by CI, `libs/*.jar`, logs and
  generated reports are ignored, `gradlew` is `100755`, the `build` job depends
  on the `parity` job, and version bump/release only run on `main`/`master`.

### B13 - License metadata contradicted the LICENSE file

- **Cause**: `fabric.mod.json` declared `CC0-1.0` and the README repeated it,
  while `LICENSE` is MIT.
- **Fix** (`723c13c`): both now declare MIT; the French mod description was
  translated for consistency.

### B14 - Dead code and debug artefacts

- Removed unused `ProfileSmoothing` and `Tr`, `TrackModel.isWoolTrace`, the
  no-op `IRON_DOOR` branch, `DBG`/`railparity.debug` blocks, the
  `grounding.debug` Gradle property, an unused lang key in 129 files, and a
  dead random-drawing loop in the scene exporter (RNG stream preserved).

## 4. Investigated and deliberately not changed

- **`NatureDesign` cross-quad gravel/litter**: the Java and Python writers
  agree, the simulator's T-junction render shows the intended gravel bed plus
  litter across the diagonally adjacent crossing, and the parity corpus covers
  it.
- **Static seeded soil RNG** (`ClassicDesign.SOIL_RNG`): soil texture depends on
  build order within a session. The `replan` scene measured it: same plan size,
  same cores, 32 soil cells differ between two identical plans. Geometry never
  depends on it (every mix block is wool-layable), so parity and gameplay are
  unaffected; left as-is to avoid changing visuals.
- **Point on top of a tall wall**: in the `wall` scene the middle control point
  sits on the wall (a player clicking the wall top), so the rail bridges over
  it and one column is 5 blocks above its neighbours; the tool never overwrites
  the player's stone bricks, and control points are authoritative heights.
  Ramping neighbours would change geometry for every scene and break the
  simulator contract, so this is reported as a known behaviour, not silently
  altered.
- **Residual preview overlays after an editor undo**: after `Ctrl+Z` the client
  level is correct (0/1365 snapshot cells differ, 17/17 cores air), but a few
  coral-shaped specks stay on screen at the former core cells. A forced chunk
  rebuild (`levelRenderer.allChanged()`) does not remove them, while an
  explicit `setBlockRenderOverride(..., null)` for the plan cells does
  (`stage-undo-rebuilt.png` versus `stage-undo-cleared.png`). The tool itself
  is clean at that moment: right after the build the harness logs
  `ghost after build: cells=0 lock=false`, and the overrider lock can be
  acquired again, so these are client-side render overrides owned by Axiom,
  not blocks and not the tool's preview. The harness clears the plan cells
  before the final screenshot; the world needs no repair and no mod behaviour
  was changed on this evidence.

### B15 - Harness: clicks and keystrokes lost at the edges of a run

These were defects in the regression harness, not in the shipped mod, and both
would have produced misleading evidence.

- **Symptom**: the first control point of a scene outside the spawn area was
  silently dropped (`control=0` after the click), and in one run the undo
  keystroke sequence had no effect.
- **Cause**: the harness clicked before the client had received the target
  chunk, so the heightmap read was a placeholder and the raycast missed; and
  the driver typed `Ctrl+Z` without checking that the editor was actually
  focused, and without any retry.
- **Fix** (`9177a6c`, `7e4777e`, `d54f9d4`): `awaitChunk` polls
  `level.hasChunkAt` with its retries at the head of the step queue, the
  harness then re-teleports onto the real surface and clicks; the driver retries
  the editor/`Ctrl+Z` sequence up to three times, and the suite only accepts an
  undo when the world is actually restored.
- **Re-test**: run `39223733867`, 118/118 in the first launch and 7/7 in the
  second; the persisted line is 153 blocks and `undo leftover=0`.

## 5. Interface rework

The tool panel was rebuilt around the single action a user needs. Nothing was
removed and no generation behaviour changed; the same `DesignOptions`, presets
and config keys are written by the same code paths.

New layout, top to bottom:

| Block | Content |
| --- | --- |
| Header | tool name in the rail accent colour, subtitle |
| Status | last message, prefixed `[i]` (green), `[!]` (warning) or `[!]` (error) |
| How to use | collapsible, three steps, open by default |
| Line | points, planned blocks, length, and a block-budget bar |
| Actions | full-width **Build rail**, then Undo point / Simplify / Clear |
| Track | density, style, orientation in a label column; six toggles in a grid |
| Classic look | collapsed: theme, ground fill, block picker or soil shares, height |
| Presets | three load/save rows |
| Debug | collapsed timings |

- Long notes wrap with `pushTextWrapPos(0)`; they used to be clipped at the
  panel edge. The subtitle and the status lines were the visible offenders.
- Every control carries a tooltip (`setItemTooltip`), so the panel can stay
  short without hiding meaning.
- The label column is 122 px: at 96 px "Planned blocks" collided with its
  value.
- Disabled states are explicit (`beginDisabled` on Simplify under four points)
  and the build button greys itself out through the same helper.
- The tool name lost its `═` prefix, which Axiom's ImGui font renders as `?`.
- 45 new translation keys in `en_us` and 46 in `fr_fr` (one pre-existing gap,
  `ui.error`, was filled in); the two files now hold the same 96 keys.
- The rewrite first wrote those keys without the `bte_railpathtool.` prefix
  (`ui.subtitle` instead of `bte_railpathtool.ui.subtitle`), which would have
  made all 45 unresolvable. Caught before the first in-game run by comparing
  every `tr()` call in `RailwayTool` against the language files, then fixed.

Verification is a real client, not a simulation: `.github/workflows/panel.yml`
launches the same Xvfb client as the test job and opens Axiom's editor, then
right-clicks three world positions and clicks **Build rail** with `xdotool`.
`docs/panel/04-built.png` shows the result: the status line reads
`[i] Rail built (48 blocks)`, the point count is back to 0, and Axiom's
History window reads `(1) Modified 48 blocks` — proof that the build went
through Axiom's own pipeline and is undoable. Every step is screenshotted in
`docs/panel/`.

Two things are not driven by the mouse, and are stated as such:
`dev/EditorShot` skips Axiom's six-step introduction, which cannot be dismissed
headless without a keyboard, and it selects the rail tool through Axiom's
`ToolManager` because the icon grid only reacts to a full press/release pair
that `xdotool` does not reproduce on llvmpipe. Both sit behind
`-Dbte.railtool.ui=true` and are inert in normal play.

## 8. Not covered

The client runs headless on a software renderer; the in-game suite issues its
actions through the mod's own callbacks, and the panel job adds real mouse
clicks (section 5). The following still needs a human:

- keyboard-driven ImGui widgets inside the panel (sliders, combos, checkboxes
  were verified visually, not clicked); Axiom's own key bindings beyond the
  `Ctrl+Z` undo used by the test suite;
- tool selection by mouse (see section 5: the screenshot job uses
  `ToolManager` instead);
- long sessions and multiplayer or dedicated-server round-trips (single-player
  save and reload are covered by the second launch);
- GPU drivers other than Mesa llvmpipe (the run proves the render path works
  and the ghost/preview is drawn, not that it looks identical on every GPU);
- the `ToolManager` reset on tool switch (documented risk, untouched).
